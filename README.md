# Rekey Relay

A browser demo of **proxy re-encryption**: a semi-trusted relay converts Alice's ciphertext into Bob's without ever holding the plaintext — and, in the construction everybody starts with, the relay and Bob together recover Alice's private key in one modular division.

**Live demo:** https://systemslibrarian.github.io/crypto-lab-rekey-relay/

---

## What It Is

Two proxy re-encryption schemes, both real, both running on the same curve so the difference between them is visible rather than described.

**BBS98** — Matt Blaze, Gerrit Bleumer and Martin Strauss, *"Divertible Protocols and Atomic Proxy Cryptography"*, EUROCRYPT 1998. The first proxy re-encryption scheme. It is ElGamal with the roles of the two ciphertext components swapped, so that the recipient's key sits alone in one of them and the message-blinding factor in the other:

```
keygen        sk = a,  pk = [a]g
encrypt to A  c1 = M + [k]g          the message half, recipient-independent
              c2 = [k]pk_A = [ka]g   the key half
rekeygen      rk = b · a⁻¹ mod r
re-encrypt    c2' = [rk]c2 = [kb]g,  c1 untouched
decrypt by B  [k]g = [b⁻¹]c2',  M = c1 − [k]g
```

Implemented here over BLS12-381's **G1**. BBS98 needs only a prime-order group where DDH is hard; BLS12-381 is a Type-3 pairing with no efficient map from G1 to G2, so the "pair the two halves and compare" DDH distinguisher has nothing to pair against. That is the SXDH assumption, and it is what makes ElGamal sound in G1. (Over a *symmetric* pairing DDH in the source group is trivially broken and this scheme would be unsound.)

**AFGH** — Giuseppe Ateniese, Kevin Fu, Matthew Green and Susan Hohenberger, *"Improved Proxy Re-encryption Schemes with Applications to Secure Distributed Storage"*, NDSS 2005; extended version ePrint 2005/028; ACM TISSEC 9(1), 2006. Specifically their **§3.1 "A Third Attempt"** — the two-component-key scheme they implemented and benchmarked, and the one people mean by "AFGH". It is *not* the Second Attempt (`pk = g^a`, `rk = g^{b/a}`), which rests on a non-standard assumption the authors give as their reason for moving on, and which leaks a different weak key.

```
keygen        sk = (a1, a2),  pk = (Z^a1 in GT,  [a2]g2 in G2)
E2 to A       alpha = [k]g1                    in G1, re-encryptable
              beta  = M · Z^(a1·k)             in GT
D2 by A       M = beta / e(alpha, g2)^a1       exponent a1, NOT 1/a1
E1 to A       alpha = Z^(a_i·k),  beta = M · Z^k,  i in {1,2}, terminal
D1 by A       M = beta / alpha^(a_i⁻¹)
rekeygen      rk = [a1]·([b2]g2) = [a1·b2]g2   in G2, non-interactive
re-encrypt    alpha' = e(alpha, rk) = Z^(a1·b2·k),  beta unchanged
```

AFGH is written for a *symmetric* pairing `e: G × G → GT`. BLS12-381 is Type-3, so the two source-group roles have to be split across G1 and G2. The split is forced rather than chosen: `ReEncrypt` pairs the level-2 ciphertext's first component against the re-encryption key, so one goes in G1 and the other in G2, and the public key follows. The public key's first component must live in **GT** — publishing `[a1]g2` would publish the collusion weak key itself, and anyone holding the public key could then decrypt every level-2 ciphertext. `a1` and `a2` are therefore sampled independently, and `test/hardening.test.ts` proves what happens when they are not.

**Security model.** Both papers prove semantic security under a decisional assumption — DDH for the ElGamal structure BBS98 is built on, extended DBDH for AFGH. **Neither claims CCA2 security**, and AFGH state explicitly that their guarantees apply "only to ciphertexts that were honestly generated by the sender; no guarantee is implied in the case of malformed ciphertexts." The `MALFORMED_RK` and `RK_MISMATCH` refusals this demo surfaces are therefore implementation hygiene, outside both papers' models — worth having, not scheme properties.

**Not production cryptography.** This is a teaching demo. Keys live in memory for one session and are discarded on reload; there is no key management, no proof of possession at key registration, and no CCA2 security. Do not use this code to protect anything.

## Exhibits

1. **The Relay** — Alice encrypts to herself, issues a re-encryption key, the proxy transforms, Bob decrypts. Four buttons, four real operations on real BLS12-381 group elements, with an **exponent ledger** filling in beside them that shows the `a` and the `a⁻¹` annihilating and the `b` landing where `a` was. The message-carrying half of the ciphertext is printed before and after the hop and compared byte for byte. Three break-it controls reach `MALFORMED_RK`, `RK_MISMATCH`, and the delegator locked out of her own ciphertext.

2. **Collusion** — the proxy contributes `rk`, the delegatee contributes his own key, and under BBS98 one division puts Alice's private key on the table. The recovered scalar is checked two independent ways: against Alice's actual key, and by recomputing `[recovered]g` and comparing it against the public key she published, which the collusion never touched. Then the recovered key opens a message written *after* the collusion. Switch to AFGH and the same attack has no analogue — but the panel does not stop there. It shows what the colluders *do* get, uses it, and then shows what it cannot open.

3. **One Hop** — the same ciphertext relayed down Alice → Bob → Carol → Dave. Under AFGH it stops after one hop with `ALREADY_REENCRYPTED`, because the key half is now in GT and no pairing consumes a GT element. Under BBS98 it never stops, and the proxy can *multiply two re-encryption keys together* to mint a delegation nobody issued. `WRONG_LEVEL` is reachable in both directions.

4. **Delegation Graph** — what the relay knows even though it never sees a message. Install edges by hand and watch the graph accumulate; under BBS98 a transitive-closure table shows the delegations the proxy can perform that nobody authorised. A second control demonstrates that a re-encryption is publicly *linkable* — the message half is byte-identical across the hop, so any passive observer can pair the input with the output.

5. **Un-delegate** — the negative claim, run rather than stated. Delegate, relay, collude once, revoke, and then read a message written after the revocation. Ends with the only move that actually retires the capability: rotate the key and re-encrypt everything.

6. **Vectors** — every published test vector this lab depends on, recomputed in your browser through the same code path the demo uses, plus the scheme transcription checks. Green because a comparison came out equal just now, not because a badge was pasted in.

A **persistent proxy panel** sits below the tabs and never unmounts. It journals every byte the relay is handed, and its "plaintext bytes found: 0" line is the result of searching that whole record for the message currently in the Relay textarea — not a label.

## When to Use It

**Use proxy re-encryption when** you have data encrypted at rest under one key, a storage service you do not want to trust with plaintext, and a need to grant read access to new parties over time — encrypted mail forwarding, encrypted file sharing, and distributed storage are the applications AFGH themselves name.

**Use AFGH rather than BBS98** whenever the two parties do not trust each other unconditionally. BBS98 requires *both* private keys to generate a delegation key, works in both directions from that one key, and surrenders the delegator's private key to any collusion. Its own authors describe it as a "symmetric proxy function" requiring bilateral trust.

**Do NOT use either of these** where you need to withdraw an already-issued delegation. Neither construction on this page can. See *What Can Go Wrong*.

**Do NOT use either** where the delegation graph itself is sensitive and the proxy is not trusted with it. The re-encryption key *is* the relationship; the proxy must hold it to do anything.

**Do NOT use BBS98 at all** in a new design. It is here because it is the origin of the idea and because its flaw is the clearest thing in the field.

## What Can Go Wrong

**Collusion, under BBS98 — total.** `rk = b·a⁻¹` is a scalar and the group order is public, so the delegatee divides his own key into it and gets `a`. Not a weakness in an assumption, not a cryptanalytic attack — one modular division. AFGH put it plainly: *"if the proxy and Bob collude, they can recover her secret key as (a/b)·b = a!"* The paper's own deployment model makes it worse, because it intends proxy keys to be **published** — under that model Bob needs no collusion at all.

**Collusion, under AFGH — bounded, not eliminated.** The colluders compute `rk^(1/b2) = [a1]g2`, the paper's *weak* secret. It opens every level-2 ciphertext under Alice's key, forever, offline, with no proxy involved, and it is a 96-byte value they can hand to anyone. What it does **not** give them is the scalar `a1` (that is a discrete logarithm in G2), any level-1 ciphertext addressed to Alice, or the ability to forge a fresh re-encryption key to a third party (that is CDH). AFGH's comparison table scores collusion-safety "Yes\*", footnoted *"indicates master secret key only"* — this demo does not round that up. The practical significance of master-secret security: if Alice uses the same key pair for Schnorr or ElGamal signatures, which are proofs of knowledge of the discrete log, she can delegate decryption without delegating signing. Under BBS98 she loses both at once.

**No revocation, in either construction here.** Deleting `rk` from the proxy works exactly as long as the proxy chooses to honour it, and if the proxy and the delegatee ever colluded it accomplishes nothing at all — the residue works offline. Neither paper offers a cryptographic un-delegation for these schemes. Absent one, Alice must rotate her key and re-encrypt everything, which is the work proxy re-encryption was adopted to avoid.

*Scope that claim carefully.* It is about the two constructions on this page, not about proxy re-encryption as a field, and it is refutable if stated flatly:

- **Cryptographic, forward-only.** AFGH's own §3.6 temporary unidirectional scheme. A trusted server broadcasts a fresh random `h_i` each period and every `rk` is pinned to it, so advancing the period invalidates all outstanding delegations at once — *"a single global change can invalidate all previous delegations without any user needing to change their public key."* The costs are a trusted beacon, an interactive rekeygen, and the fact that a stale key still re-encrypts anything encrypted **during** its period. Also Liu, Wang and Wu, *"Time-based proxy re-encryption scheme for secure data sharing in a cloud environment"*, Information Sciences 258:355–370, 2014.
- **Scope narrowing, frequently miscited as revocation.** Weng, Deng, Ding, Chu and Lai, *"Conditional proxy re-encryption secure against chosen-ciphertext attack"*, ASIACCS 2009; Tang, *"Type-Based Proxy Re-encryption and Its Construction"*, INDOCRYPT 2008; Liang, Cao, Lin and Shao, *"Attribute based proxy re-encryption with delegating capabilities"*, ASIACCS 2009. These bind a delegation to a keyword, a type or an attribute policy. None of them revokes anything: once the condition is fixed and the key is out, the proxy re-encrypts every matching ciphertext forever.
- **The underlying limit.** A re-encryption key is a capability over a ciphertext *set*, not over a session. Revocation can shrink which future ciphertexts join that set; it cannot claw back one already in it. Schemes that update `rk` on revocation must also update the stored ciphertexts, which is "rotate and re-encrypt" relocated to the server — effective only if the server actually runs the pass and discards what came before.

**Nothing is non-transferable.** AFGH's table scores non-transferability "No" for every scheme in it, including their own, noting that no scheme achieves it. Once a colluding pair holds the residue they can pass it on.

**Metadata.** The proxy always learns who delegates to whom. Worse, a re-encryption is publicly linkable by anyone: the message-carrying half is byte-identical before and after, so an observer pairs input to output with a string comparison, no proxy cooperation required. For many deployments that graph is the sensitive part.

**Transitivity, under BBS98.** `rk(A→B) · rk(B→C) = rk(A→C)`. The proxy composes delegations on its own. The original paper says so: *"The proxy relationship is necessarily transitive."*

**Original access, under AFGH.** After a re-encryption, the ciphertext belongs to Bob and Alice can no longer read it. AFGH score this property as achievable only with extra overhead — an additional retained term, which they note "may impact proxy invisibility". This lab ships the scheme as written, so the cost is visible rather than hidden behind a stored copy.

**Rogue key registration.** Neither scheme requires a proof of possession. If Mallory registers Carol's published `[b2]g2` as his own, `rk(A→Mallory)` is bit-identical to `rk(A→Carol)` — and *Carol*, not Mallory, is the one who can open the result. Key registration is out of scope for both papers' models; a deployment needs a proof of possession at registration.

**Self-delegation.** `rk(A→A) = [a1·a2]g2`, and Alice knows `a2`, so anyone holding both recovers her own weak key `[a1]g2` — the full collusion residue with only one party involved.

**Subgroup safety.** BLS12-381 is *not* subgroup-secure: the cofactors of all three groups contain prime factors smaller than `r`. `@noble/curves` validates curve and order-r subgroup membership in `G1.Point.fromBytes` and `G2.Point.fromBytes`, but `Fp12.fromBytes` validates neither. Every place this lab raises a *received* value to a secret exponent — a delegatee opening a level-1 ciphertext the proxy handed him — checks `x^r == 1` first. That test is complete rather than heuristic, because `Fp12*` is cyclic.

**Serialization is not interoperable.** The data-encryption key is derived from `@noble/curves`' Fp12 byte order. There is no standardized compressed encoding for GT and libraries differ in their Fp12 tower construction, so another implementation of this scheme would derive a different key from the same group element. That is a property of this demo, not of the scheme.

## Real-World Usage

Proxy re-encryption's flagship application is the one AFGH built: **encrypted distributed storage**, where a file server holds ciphertext it cannot read and re-encrypts on demand for authorised readers. Their paper reports an implementation over Chefs, a read-only networked file system. The idea has since carried into encrypted-email forwarding, key escrow with limited scope, DRM key distribution, and blockchain-adjacent data-sharing systems where a network of proxies performs the transform.

It has never become ubiquitous, and the reasons are visible on this page: the collusion story is subtle, the delegation graph leaks, the revocation story is bad, and the single-hop constructions with the best security properties are exactly the ones that cannot chain. Where a system can tolerate a key server that *does* see plaintext, or can afford to re-encrypt on write, the simpler design usually wins.

The pairing library here, `@noble/curves`, is the same audited implementation used in production Ethereum and post-quantum tooling. The BLS12-381 curve is the one used for Ethereum's consensus signatures, Zcash's Sapling circuits, and drand's randomness beacon.

## Performance

Measured in Chromium on a 2023 Apple laptop, averaged over repeated runs after warm-up, through the same code path the page uses.

| operation | cost | why |
|---|---|---|
| BBS98 re-encrypt | ~1 ms | one G1 scalar multiplication, and nothing else |
| BBS98 decrypt | ~2 ms | one G1 multiplication, one subtraction, HKDF + AES-GCM |
| BBS98 encrypt | ~4 ms | three G1 multiplications plus the hybrid layer |
| AFGH keygen | ~7 ms | one G1 multiply, one G2 multiply, one GT exponentiation |
| AFGH re-encrypt | ~7 ms | exactly one pairing |
| AFGH level-2 encrypt | ~12 ms | one G1 multiply plus two GT exponentiations |
| AFGH level-2 decrypt | ~12 ms | one pairing plus one GT exponentiation |
| AFGH level-1 decrypt | ~12 ms | one GT exponentiation; no pairing |
| one BLS12-381 pairing | ~7 ms | the floor under every AFGH operation |

BBS98 is roughly three to ten times faster than AFGH per operation, and gives up the delegator's private key to a single collusion. That is the trade in one line.

Ciphertext sizes follow the same shape. A BBS98 ciphertext is 96 bytes of group elements (two compressed G1 points); an AFGH level-2 ciphertext is 624 (one G1 point plus one GT element); an AFGH level-1 ciphertext is 1152 (two GT elements). GT elements are large because Fp12 has no standardized compressed form. On top of each sits the AES-GCM payload: a 12-byte nonce, the plaintext, and a 16-byte tag.
